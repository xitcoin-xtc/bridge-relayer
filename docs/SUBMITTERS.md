A successful `check` is offline only and always reports `ready: false` and
`submissions: 0`. Nothing in this repository deploys, provisions, enables or
starts a service.

## Disabled manifest and immutable release

Provision one root-owned regular JSON file at
`/etc/xitcoin-bridge/submitter-xitcoin.json` and one at
`/etc/xitcoin-bridge/submitter-cronos.json`. Group/world write access is rejected.
All parent directories must be root-owned, non-symlink directories without
group/world write access. Reads use `O_NOFOLLOW` and `O_NONBLOCK`, enforce a
16 KiB limit before and during reading, and reject malformed UTF-8 and JSON.
Unknown fields and type coercions are rejected. No endpoint or credential
fields are supported.

The complete manifest schema is illustrated below. Replace `RELEASE_COMMIT`
with the full lowercase 40-character Git commit of the reviewed release;
the literal placeholder is intentionally invalid. Change only `destination`
to `cronos` for the second instance.

```json
{
  "version": 1,
  "mode": "disabled",
  "destination": "xitcoin",
  "releaseCommit": "RELEASE_COMMIT",
  "routeId": "0x21121c16b53a726056a6683f00c7eb4da5501ce8a2abc8a4677e06f1e94b5cd9",
  "cronosChainId": 338,
  "xitcoinChainId": "xitcoin-testnet-v2-1"
}
```

The CLI resolves its own real path and requires
`/opt/xitcoin-bridge-relayer/<releaseCommit>/src/submitter-cli.js`.
It checks root ownership and absence of group/world writes on the file and
all parent directories. A `current` symlink may select that immutable directory;
a moving name in the manifest, a different resolved commit or a checkout in a
writable directory is rejected. Source-tree checks consequently fail release
validation by design.

Root provisioning must verify the Git commit and reproducible release contents,
including dependencies, and make the entire release tree root-owned and
non-writable by service identities. The runtime trusts that provisioned tree;
a directory named after a commit is not cryptographic proof of its contents.
Never modify an installed release in place. No provisioning or activation is
performed by these modules.

From a provisioned release, the offline commands are:

```sh
npm run submitter:check -- xitcoin /etc/xitcoin-bridge/submitter-xitcoin.json
npm run submitter:check -- cronos /etc/xitcoin-bridge/submitter-cronos.json
```

With a disabled manifest, `npm run submitter:start -- <destination> <manifest>`
is blocked for both destinations. The generic systemd template uses that same
public startup path, denies IP networking, disables core dumps and does not
restart a blocked process. Keep both instances disabled. Check success is not
readiness, preflight success or authorization.

### Durable duplicate-broadcast protection for both destinations

Update: the durable layer described below now exists as
[`src/broadcast-ledger.js`](../src/broadcast-ledger.js) and
[`src/durable-broadcast.js`](../src/durable-broadcast.js). See
[Durable broadcast ledger](#durable-broadcast-ledger). The paragraph that
follows describes the original phase-one gap.

The existing helper checks destination status before sending, saves the returned
transaction reference and resumes submitted/completed rows without resending.
Its staging tests cover canonical processed-status recovery and normal retries.
It does not atomically claim a transfer across concurrent workers or persist a
broadcast intent before the network call. A crash after acceptance but before
saving the reference, combined with a pending transaction absent from canonical
status, is not covered by that helper alone.

Before connecting a broadcaster, persist an exclusive transfer claim and the
exact signed transaction identity before sending. Define recovery that reconciles
pending and finalized state without creating a second transaction; an ambiguous
outcome must halt rather than authorize a fresh broadcast. Test competing
processes, restarts, nonce conflicts, timeouts, RPC disagreement, reorganization,
failed execution and all crash boundaries with durable storage. Revalidate the
persisted approval request against the transfer, route and authorized quorum.
Do not mutate existing approvals, reset lifecycle state or delete pending rows
to permit retries.

Phase one leaves the store and submission helper unchanged. Source review shows
that this runtime imports only manifest validation and filesystem reads; it has
no store or broadcast dependency. Tests verify repeated inspection returns the
same disabled report and repeated startup refuses, plus CLI failure handling
and systemd network denial. These tests do not instrument network calls or
assert that an on-disk lifecycle store remains unchanged.

## Durable broadcast ledger

`BroadcastLedger` is one exact-schema SQLite database per destination
submitter account. It reuses the private-path checks of the offline journals
(Linux service identity `xitcoin-bridge-submitter-<destination>`, private
service-owned parent, `O_NOFOLLOW` traversal, inode rechecks), immediate
transactions, `synchronous=FULL` and WAL. Exclusive creation initializes it;
reopening requires the identical table DDL, constraints, triggers, version and
binding. There is no migration, repair, delete, reset, expiry or retry API.

The binding is the destination deployment identity: destination, chain ID,
route, target (Cronos vault address or the Xitcoin bridge module), target
identity (Cronos runtime code hash or the pinned chain schema commit) and the
submitter account. It deliberately excludes the release commit so that a
reviewed upgrade with the identical schema can resume pending state instead of
abandoning it. Cronos chain ID `25` and the empty-code hash are rejected.

The ledger enforces, in one fenced immediate transaction per change:

- a worker lease with a fencing epoch. Another worker may take over only after
  expiry, which increments the epoch; every later write by the previous holder
  fails;
- one row per transfer (`claimed`), created only by the lease holder, bound to
  its immutable RelayStore source reference, and at most one unfinished
  transfer per account;
- exact signed bytes, their SHA-256 digest, the destination transaction hash
  and the account nonce committed (`signed`) before any send. Nonces are
  strictly sequential; a transaction hash, digest or nonce can never be reused
  by another transfer, and bytes can never be replaced;
- a write-ahead `broadcast` marker committed before every send of those
  identical bytes, bounded to at most 32 attempts (destination policy may be
  lower);
- forward-only states `claimed -> signed -> broadcast -> finalized | failed`,
  plus `halted` from any unfinished state. `finalized`, `failed` and `halted`
  are permanent, and any `failed` or `halted` row blocks every new claim until
  an offline review;
- two permanent states that never block the queue: `released_elsewhere` (the
  destination released this transfer in another finalized transaction, which
  the adapter verified; it records that transaction and its block) and
  `rejected` (this transfer alone can never be sent, for example an invalid
  recipient). `released_elsewhere` is allowed without bytes or after our
  identical bytes were sent, never from `signed`, so a reserved nonce is never
  left unused. `rejected` is allowed only without bytes;
- durable deferrals: a transfer that cannot proceed yet (for example an expired
  approval awaiting re-issue) is skipped until a backoff expires (1 minute,
  doubling, at most 1 hour). A deferral is a scheduling hint only: it never
  changes a transfer row and is never permission to send;
- a claimed row has no bytes and was never sent, so it may be rebound to a
  re-issued approval. Once bytes exist the approval digest is permanent;
- `unclaimed`: a claimed row (no bytes, no nonce) whose transfer cannot
  proceed yet, for example because its approval expired during downtime, is
  released and deferred so it never holds the single unfinished slot. It may
  be claimed again later;
- two more permanent states that never block the queue and are counted in
  every cycle report (`attention`) until an operator reviews them: `expired`
  (our identical bytes were mined and reverted after the approval deadline,
  consuming their nonce; the burn still awaits a new approval and RelayStore
  keeps it `submitted`, in flight) and `release_unverified` (the outcome
  could not be verified: the destination reports the transfer processed but
  no matching release was found, or history about our mined transaction is no
  longer served; never a completion, RelayStore unchanged; the reason code is
  kept in the transfer's event history). `rejected` rows are counted too, and
  so are `reverted` rows: our bytes were mined before the deadline and
  reverted under a guardian pause or for a lasting condition of this transfer
  (daily release limit exhausted, insufficient liquidity, amount above the
  release limit, signer-set rotation), as shown by vault state on every
  origin. Their nonce is consumed and retrying would need a second
  transaction for the transfer, which the ledger forbids, so the transfer is
  parked without blocking the queue. Out of gas or any unexplained revert
  stays `failed` (blocking).

SQLite triggers repeat these rules (no delete, no regression, no replacement,
immutable source reference, sequential nonce, monotonic lease epoch) as defense in depth against
accidental raw writes. Every read rehashes stored bytes. The bytes are opaque
to the ledger; the destination adapter validates them against the approved
request on every use. As with the offline journals, a malicious local owner,
root, or a consistent restore of an older database is outside SQLite
self-consistency guarantees and is not detected.

`runDurableSubmissionCycle` composes the ledger with RelayStore and a trusted
destination adapter (chain reads, signing and byte validation). It owns the
ordering:

1. reject any blocking ledger row; reconcile every RelayStore `submitted` row
   (keyset pages, never a fixed window, because expired, reverted and
   unverified rows stay `submitted`), each of which must reference a
   transaction the ledger holds; find an unfinished
   transfer by the source reference stored in its ledger row (never by a
   bounded window over RelayStore rows);
2. otherwise walk all `approved` transfers in order with keyset pagination,
   skipping rejected and still-deferred ones, and assess at most 8 per cycle;
3. read the persisted approval request and approvals under size bounds and
   bind their exact stored text by SHA-256 (`requestHash`). The adapter
   revalidates the request against the transfer, route and authorized quorum
   and decides `sign`; `wait` scoped to the route (for example a paused vault:
   the cycle stops) or to the transfer (it is deferred and the walk moves on);
   `reject`; `released_elsewhere`; `release_unverified`; or `halt`. Nothing is
   claimed unless it decides `sign`, and a transfer-scoped wait on a claimed
   row releases the claim (`unclaimed`);
4. claim, sign, and commit the bytes before anything else;
5. bind RelayStore to that single transaction hash (`approved -> submitted`);
6. commit the broadcast marker, then send the identical bytes. Send errors are
   never decision inputs, and the first observation happens in a later cycle;
7. observe: `pending`, `wait`, `rebroadcast` (identical bytes only, when the
   adapter proves the transaction is unknown and its nonce unused),
   `released_elsewhere` (our bytes reverted because another finalized
   transaction released the transfer first, for example by copying our
   pending calldata), `expired` (our bytes reverted after the approval
   deadline), `reverted` (before the deadline, for a lasting condition of this
   transfer), `release_unverified`, `failed` (any other finalized failed
   execution; permanent and blocking), `finalized`, or a persisted `halt`;
8. complete RelayStore only after the ledger records finality or a verified
   release elsewhere. `destination_ref` keeps referencing only our own
   transaction (or none if we never signed); the new `release_ref` column
   records the transaction that actually executed the release (ours, or the
   other transaction), where a reconciler reads RelayStore.

RelayStore opens with a bounded 5-second busy timeout because the coordinator
and the Cronos submitter both write it; a longer lock fails with `SQLITE_BUSY`,
which callers treat as a temporary condition (`isRelayStoreBusy`).

A changed stored request or approval, a RelayStore reference to any other
transaction, a RelayStore `submitted` row without ledger custody, or a
malformed adapter decision halts or fails closed. The RelayStore is never
ahead of the ledger, and lifecycle state is never reset.

Tests use real SQLite files: competing child processes, expired-lease
takeovers, SIGKILL at every ledger commit and inside an uncommitted signed
write, fencing, trigger enforcement, incompatible schema/binding, filesystem
attacks, and engine crash points at every boundary (claim, signed, RelayStore
submitted, broadcast marker, sent, ledger finalized, RelayStore completed) for
both destinations. Engine tests use a deterministic in-memory destination model
for reorganization, lost and ambiguous sends, bounded attempts, failed
execution, nonce conflicts, releases by another transaction (before any claim,
after signing, after a drop, and a front-run of our pending transaction),
rejected transfers, pauses, durable deferrals that do not starve later
transfers, a backlog of 300 approved transfers, RPC failures and tampering;
a child process holding a RelayStore lock covers the busy timeout. That model is not a chain adapter. These
are process-crash tests, not power-loss or storage-rollback proofs.

The engine itself starts nothing. The [Cronos testnet submitter](#cronos-testnet-submitter)
and the [Xitcoin testnet submitter](#xitcoin-testnet-submitter) connect it to
startup, each behind an explicit testnet manifest, with adapters that provide
independent, bounded canonical observations for every decision.

## Cronos testnet submitter

### Manifest

`submitter:start cronos` runs only with this exact schema in the root-owned
manifest (same file, ownership and release rules as the disabled manifest).
Every value is pinned; nothing is discovered or defaulted. Unknown or missing
fields, type coercions, getters, mainnet chain ID `25`, a Xitcoin destination,
non-checksummed addresses, the empty-code hash and RPC URLs with credentials,
query strings or fragments are rejected. Endpoints must be independent HTTPS
origins; loopback `http` is accepted only with `allowLoopbackHttp: true`, for
reviewed local tunnels. The manifest never contains a key or password.

```json
{
  "version": 1,
  "mode": "testnet",
  "destination": "cronos",

  "routeId": "0x21121c16b53a726056a6683f00c7eb4da5501ce8a2abc8a4677e06f1e94b5cd9",
  "cronosChainId": 338,

```

Placeholders are intentionally invalid. Bounds: `confirmations` 2–10000,
`gasLimit` 21000–10000000, `maxGasPrice` at most 10000 gwei, `maxFee` must cover
`gasLimit * maxGasPrice`, `minDeadlineMarginSeconds` 30–3600,
`maxBroadcastAttempts` 1–32, `releaseLookbackBlocks` 1000–1000000,
`logRangeBlocks` 100–10000 (keep it within the providers' `eth_getLogs` range
limit), `cycleIntervalMs` 1000–60000, 2–4 RPC origins per chain. `cronosRouteId` must equal the deployed testnet vault route
(`TESTNET_ROUTE_ID`), never a hash of the Xitcoin route label. The signer set
and version must equal the vault's on-chain values. `vaultCodeHash` is
`keccak256(eth_getCode(vault))` of the deployed runtime code. The runtime code
embeds immutables (asset, route, EIP-712 chain and address), so the hash is
deployment-specific: compute it from the deployment on independent providers
and cross-check it against a reproducible build of the pinned contracts commit
with those immutables before pinning it.

`check` validates the manifest and release offline and reports
`mode: "testnet"`, `ready: false`, `submissions: 0`. Only `start` performs
chain, vault, keystore and durable-state checks.

### Startup and process model

`start` loads the manifest and release, then refuses unless every RPC origin
reports chain ID `338`. It loads the submitter key only through the existing
secure keystore adapter (`keystorePath` owned by the service identity, mode
`0600`, password from the systemd credential `keystore-password` in
`$CREDENTIALS_DIRECTORY`; no environment-variable or command-line secret) and
requires the decrypted account to equal `submitter`. It opens the existing
RelayStore (never creating an empty one) and the broadcast ledger bound to the
vault, code hash and submitter account, then runs one durable cycle per
`cycleIntervalMs`. Conditions that persist nothing and may clear by themselves
(transport failures, origins disagreeing, deadline or release evidence that not
every origin confirms yet, a RelayStore locked by the coordinator beyond its
5-second busy timeout) pause the loop and retry with bounded backoff (up to 5
minutes), logging `temporarily_stopped` with a stable code. A persisted halt, a
finalized failed execution, an identity or configuration mismatch, or any
unknown error stops the process with a stable code; it does not restart itself.
SIGTERM finishes the current cycle and releases the worker lease.

### Transport

Each RPC origin uses a bounded JSON-RPC client: one overall deadline covers
connection, headers and every body read; streamed bytes are counted against a
fixed limit before retention and before JSON parsing; parsed JSON is bounded in
depth and node count; redirects are refused; JSON-RPC version and request ID
must match; errors are reduced to stable codes without URLs or upstream text.
Every origin must answer every query. Identity reads must agree exactly across
origins. The Xitcoin CometBFT client receives only byte-bounded bodies through
the same transport.

### Checks before signing (nothing is claimed if any fails)

- every origin reports chain ID `338`;
- at the finalized height (`tip - confirmations`, identical block hash on every
  origin): vault runtime code hash equals the pinned hash, `routeId()` equals
  the pinned route, `signerSetVersion()` equals the pinned version and
  `signers()` equals the pinned set;
- the persisted approval request is exactly what the coordinator derives from
  the stored finalized source transfer, route, vault and signer version, and the
  stored approvals form a recovered, authorized, strictly ordered 2-of-3 quorum
  with vault-compatible recovery bytes (`27`/`28`);
- the recipient is a valid address other than zero, `0x...dEaD` and the vault;
  otherwise the transfer is `rejected` (the vault would refuse it forever) and
  the queue moves on. Signers refuse such approvals too;
- the deadline leaves at least `minDeadlineMarginSeconds` against both the local
  clock and the latest block timestamp; otherwise the transfer is deferred until
  re-issue;
- amount within `maxAmount` and the vault's `maxReleaseAmount` (otherwise
  deferred);
- on every origin at the latest block: vault not paused (`route_paused` stops
  the cycle), `processedBurns(sourceBurnId)` false, liquidity at least the
  amount (otherwise deferred). If every origin reports the burn processed, the
  submitter looks for the vault's `Released` event for it (see
  [Releases by other transactions](#releases-by-other-transactions));
- the Xitcoin source burn is re-verified as canonical and finalized on
  independent CometBFT origins;
- gas price (maximum across origins) within `maxGasPrice` and the submitter
  balance covers `gasLimit * gasPrice` (otherwise the cycle waits);
  `eth_estimateGas` within `gasLimit` and an `eth_call` simulation of the exact
  release succeed on every origin. A revert counts only when every origin
  reports an execution error (the transfer is then deferred); a rate limit
  (for example `-32005`), any other provider error or mixed answers is a
  temporary stop, never a decision about the transfer;
- account nonce: `latest` equals `pending` on every origin (no foreign pending
  transaction) and equals the ledger's next nonce (after the first transfer).

The submitter signs one legacy (type 0) EIP-155 transaction for chain `338` with
`gasLimit` from the manifest and the observed gas price. The reviewed release
plan and signed-byte inspector re-check every field before the ledger commits
the bytes, hash and nonce. Then RelayStore records `submitted` with that hash,
the broadcast marker is committed, and the identical bytes are sent to every
origin. Before the first send the deadline is checked first: once the local
clock says the margin is lost, the stored bytes are sent without simulation or
nonce checks, so their reserved nonce is consumed whatever the origins do
(sending our own committed bytes is never unsafe). Only the pause flag is read
first, from a strict majority: a known guardian pause still holds the row
(`route_paused`; after the resume the bytes are sent and, past the deadline,
end `expired`), and only when that read fails are the bytes sent without it.
Otherwise the
nonce, pause, replay flag, latest block time and a simulation of the exact
signed transaction are read from a strict majority of origins: with three or
more origins one faulty origin no longer holds the row until its approval
expires. These reads only decide to send or wait; a persisted halt
(`nonce_consumed_before_send`, `account_nonce_regressed`,
`foreign_pending_transaction`) still requires every origin to agree. If the
origins report the burn processed or the deadline margin lost, the stored bytes
are sent without simulation; a revert after the deadline is then recorded as
`expired`.

Remaining exposure: with two origins (the minimum) a strict majority is both,
so one faulty origin still holds a signed row until the local deadline margin
is lost, at which point its bytes are sent and the transfer typically ends
`expired`, needing a new approval. Configure three or more independent
origins. Confirmation, completion and every halt still need all origins.

### Confirmation

A transfer completes only when, on every origin: the receipt is identical and
names the submitter, the vault and the persisted hash; the provider transaction
equals the persisted bytes field by field (input, nonce, gas, price, value,
chain, signature); its block is canonical; exactly one non-removed `Released`
event from the vault matches source burn ID, recipient, amount and signer
version (the transaction input binds every approved field, including the
deadline and signatures); the block is at least `confirmations` deep; and
`processedBurns` is true at the finalized height. Then the ledger records
`finalized` and only afterwards RelayStore records `completed`.

### Releases by other transactions

`release()` is callable by anyone holding valid approvals, so a third party may
release a burn first, for example by copying our pending calldata with a higher
gas price. That is not a failure: the recipient received exactly the approved
amount. When every origin reports the burn processed, the submitter searches
the vault's `Released` event for that burn ID backwards over at most
`releaseLookbackBlocks`, in `logRangeBlocks` chunks: first back from our own
receipt block when our transaction was mined (a front-run is mined no later
than our revert), then back from the highest block at or before the approval
deadline (no release using this request or an earlier one can be later;
re-issues only extend the deadline). That deadline block is searched only
within the last `releaseLookbackBlocks` blocks, never from block 0. Origins
must serve at least that much recent block and log history. Older history that
an origin explicitly cannot serve (a null block or a JSON-RPC error, as from a
pruned or state-synced provider) makes the search unreachable rather than
temporarily failing forever; transport failures remain temporary. It requires on every
origin: an identical log whose topics and data match source burn ID, recipient,
amount and signer version; a successful receipt containing it; a canonical
block; and finality depth. The ledger then records `released_elsewhere` with
that transaction and block, RelayStore records `completed` (still referencing
only our own transaction, or none), and the queue moves on.

- Before any claim, or with a claimed row: no transaction is sent.
- After our bytes were committed but before their first send, or after they
  were dropped: the identical bytes are sent once anyway. They revert, but they
  consume the nonce the ledger reserved for them, so later transfers keep
  strictly sequential nonces.
- Our transaction reverted because the burn was already processed: recorded as
  released elsewhere instead of `failed`.
- A `Released` event for the burn that does not match the approved fields (or
  more than one) halts (`processed_with_mismatching_release`), even when it is
  returned by a single origin while others fail or no longer serve that
  range: only a compromised signer quorum (or a lying origin, settled in the
  offline review) produces one, and a halt is preferred to an alert. Evidence not
  yet final defers the transfer. If the burn is processed at a finalized
  height and no matching release is found (`release_not_found`), or the
  history to search is no longer served (`release_history_unserved`), the
  ledger records `release_unverified`: a persistent, non-blocking alert
  reported in every cycle, never a completion.
- Our own mined transaction older than the last `releaseLookbackBlocks`
  blocks whose receipt, transaction or block some origins no longer serve
  (null or a JSON-RPC error, after downtime longer than an origin's
  retention), with our nonce consumed on every origin, is recorded
  `release_unverified` (`receipt_history_unserved`); so is a revert whose
  classifying state is no longer served (`revert_history_unserved`). A
  receipt that only some origins return is not proof on its own: it is
  history no longer served only when a strict majority of origins serve the
  claimed block, with the receipt's block hash, containing our transaction (a
  pruned transaction index). When a strict majority serve that block without
  our transaction, or there is no strict majority either way (for example
  origins that no longer serve the block), it fails closed: unless an origin
  that lacked the receipt now sees our transaction (indexing lag), the row
  halts `nonce_consumed_without_receipt` with our nonce used on every origin,
  exactly as when no origin returns a receipt. With three or more origins no
  single origin can force or suppress that key-compromise tripwire (it can
  only hold it pending); with two, one origin can still force the halt, and
  an origin that has pruned the block halts the row too. Run three or more
  origins with the required retention. Recent
  history missing on an origin is indexing lag and transport failures stay
  temporary. Origins must retain at least the maximum expected downtime plus
  `releaseLookbackBlocks` (see [OPERATIONS.md](OPERATIONS.md#cronos-testnet-submitter)).

Recovery decisions (all from canonical observations, never from send errors):

| Observation | Action |
| --- | --- |
| receipt absent on some origins, mined within the last `releaseLookbackBlocks` | wait (indexing lag) |
| our receipt older than that and returned by some origins only, a strict majority serving the claimed block with our transaction, nonce consumed on every origin | `release_unverified` (`receipt_history_unserved`); queue continues |
| our receipt older than that and returned by some origins only, without such a majority (a majority serves the block without our transaction, or none either way), nonce consumed on every origin | halt `nonce_consumed_without_receipt` |
| our included transaction or block older than that and no longer served by some origins (null or JSON-RPC error) while every origin returns the receipt, nonce consumed on every origin | `release_unverified` (`receipt_history_unserved`); queue continues |
| receipts or included transactions differ between origins, or content disagrees | temporary stop (`rpc_disagreement`), retried |
| transaction pending on any origin | wait |
| unknown everywhere, nonce unused, not processed, not paused, attempts left | resend the identical persisted bytes (also after the deadline: they then revert and consume the nonce) |
| unknown everywhere and the account nonce advanced | halt `nonce_consumed_without_receipt` |
| a foreign pending transaction from the account | halt `foreign_pending_transaction` |
| unknown everywhere, nonce unused, released by another transaction | resend the identical bytes once (they revert and consume the nonce), then record `released_elsewhere` |
| receipt, event or input mismatch returned identically by every origin | halt |
| reorganized block | wait, then observe again (resend identical bytes if dropped) |
| finalized revert because another transaction released the burn | `released_elsewhere`; RelayStore `completed` with `release_ref`; queue continues |
| finalized revert, burn processed, no matching release found | `release_unverified` alert; queue continues |
| finalized revert in a block later than the approval deadline | `expired`; queue continues |
| finalized revert before the deadline under a guardian pause, or explained by daily limit, liquidity, release limit or signer rotation (every origin) | `reverted`; queue continues |
| finalized revert before the deadline whose classifying state is older than `releaseLookbackBlocks` and no longer served | `release_unverified` (`revert_history_unserved`); queue continues |
| any other finalized failed execution (status `0`, including out of gas) | ledger `failed`; stop; never retried |

Revert classification. Standard RPC cannot read state at a position inside a
block. The pause is reconstructed exactly: the vault changes it only with
`Paused` and `Unpaused` events, which are replayed from the state at the end
of the previous block up to our transaction index (and must end in the state
read at the end of the inclusion block). Signer set, limits and liquidity
count only when the condition holds both at the end of the previous block and
at the end of the inclusion block, so a change made by another transaction in
the same block is never taken as the cause; such a revert stays `failed` for
review. The classification only decides blocking versus non-blocking; it never
completes a transfer or sends anything.

Every persisted halt is based on evidence that every origin returns
identically, with two exceptions where a halt is preferred to an alert: a
mismatching `Released` event, and an old receipt for our transaction that a
strict majority of origins does not confirm in the claimed block (with two
origins, one origin can force that halt; both above). Otherwise a
single origin (stalling, rate limiting or lying) can only cause a temporary
stop or a non-blocking alert, and no approval deadline can turn a provider
fault into a queue-wide halt.

## Xitcoin testnet submitter

Submits each approved Cronos deposit to Xitcoin as one signed Cosmos
transaction carrying `MsgSubmitAttestation`, through the shared durable engine
and ledger described above, with the same guarantees as the Cronos submitter:
exact signed bytes, transaction hash and sequence committed before any send,
at most one transaction per transfer and per sequence, recovery by observation
or by resending the identical bytes only, and halts only on evidence every
origin returns identically.

It depends on the typed bridge queries and processing records of pos-chain
`xitcoin-security-hardening-v2` (pos-chain #102 and #104, see
[bridge-architecture.md#queries](https://github.com/xitcoin-xtc/pos-chain/blob/main/docs/bridge-architecture.md#queries)).
That upgrade is not deployed on `xitcoin-testnet-v2-1` yet.

### Startup and process model

`start` loads the manifest and release, then refuses unless every Xitcoin
origin reports chain ID `xitcoin-testnet-v2-1` (`xitcoin` stops with
`xitcoin_mainnet_rejected`) and is not catching up, and every Cronos origin
reports chain ID `338`. The key is loaded only through the secure keystore
adapter (service-owned `keystorePath`, mode `0600`, password from the systemd
credential `keystore-password`); its account must be the pinned `submitter`
and its compressed public key is used in the transaction's signer info. It
opens the existing RelayStore (never creating one) and the broadcast ledger
bound to the destination, chain ID, route, `x/bridge`, `chainSchemaCommit` and
submitter account, then runs one durable cycle per `cycleIntervalMs`.
Temporary conditions (transport failures, origins disagreeing or catching up,
indexing lag, a RelayStore locked by the coordinator, source finality not yet
verified) pause the loop with bounded backoff and log `temporarily_stopped`
with a stable code. A persisted halt, a failed execution, an identity or
configuration mismatch or any unknown error stops the process; it does not
restart itself. SIGTERM finishes the current cycle and releases the worker
lease. `ops/systemd/xitcoin-bridge-submitter-xitcoin-testnet.service` is the
review-only template.

### Transport and origins

Each origin is one operator's CometBFT RPC (JSON-RPC over POST: `status`,
`block`, `tx_search`, `unconfirmed_txs`, `abci_query` for the tx service's
`Simulate`, `broadcast_tx_sync`) and Cosmos SDK REST API (the typed
`/xitcoin/bridge/v1/` queries, `/cosmos/auth/v1beta1/accounts`,
`/cosmos/bank/v1beta1/balances`, `/cosmos/evm/feemarket/v1/params`). Every
read uses the bounded transport (one overall deadline, streamed byte limit,
bounded JSON depth and node count, no redirects, sanitized stable error codes).
The only header a request may add is `x-cosmos-block-height` (decimal), for
reads at one committed height, whose answers must report that height. Every
answer is normalized to the exact canonical shape the adapter uses: exact key
sets for the typed queries, decimal strings without leading zeros, `0x`
lower-case or upper-case hexadecimal exactly where the chain prints them,
EIP-55 signer addresses, RFC 3339 UTC block times, base64 that round-trips,
transaction bytes whose SHA-256 is the requested hash, and attestation
answers whose `status`, `processed` and `record` agree. Anything else is
rejected, never coerced. Upstream log text is never kept or logged.

Two origins are the minimum and are accepted for testnet. Production needs
three or more independent operators: with two, a strict majority is both, so
one faulty origin can hold a signed row until its approval deadline margin is
lost (the identical bytes are then sent and typically end `expired`). With any
number of origins, one origin returning a mismatching attestation record forces
the halt described below, and one origin failing every read stops completion
temporarily. Origins must run the `kv` transaction indexer and serve state,
blocks and the transaction index for at least `historyBlocks` recent blocks
plus the maximum expected downtime.

### Checks before signing (nothing is claimed if any fails)

- every origin reports chain ID `xitcoin-testnet-v2-1` and is not catching up;
- the persisted approval request is exactly what the coordinator derives from
  the stored finalized Cronos deposit, route ID, vault and chain IDs, and the
  stored approvals form a recovered, authorized, strictly ordered 2-of-3
  quorum for its digest;
- the recipient is a canonical 20-byte `xtc` account other than the zero and
  `0x…dEaD` accounts; otherwise the transfer is `rejected` (never sent) and the
  queue moves on;
- the deadline leaves at least `minDeadlineMarginSeconds` against both the local
  clock and the latest block time (the chain rejects a block time after the
  deadline); otherwise the transfer is deferred until re-issue;
- on every origin, identical: bridge parameters (chain ID, `axtc`, 2-of-3,
  attestation and source-deposit domains) and the route (stored route ID,
  source chain `338`, the pinned signer set and signer set version). One origin
  answering differently is a temporary stop; all origins agreeing on another
  identity stops the process (`signer_set_mismatch`, …);
- route enabled and not paused on every origin (otherwise `route_paused`, the
  cycle stops without claiming); amount within `maxAmount` and the route's
  `max_transfer_amount`; remaining daily limit and outstanding cap at least the
  amount on every origin (otherwise deferred);
- the attestation query (`/xitcoin/bridge/v1/attestations/{id}`, the
  source-deposit replay key) reports `ABSENT` on every origin. Processed by
  another transaction: see below. Origins disagreeing: deferred;
- the Cronos deposit is re-verified as canonical and finalized on the
  independent Cronos origins (vault, route, depositor log, receipt, block);
- the account exists with the same account number on every origin and no
  other public key; the sequence is identical on every origin;
- price per gas = `ceil(max over origins of max(base fee, min_gas_price) ×
  feeMultiplierPercent / 100)` axtc, at most `maxGasPrice` (otherwise the
  cycle waits);
- a simulation of this exact message (`abci_query` of
  `/cosmos.tx.v1beta1.Service/Simulate`) succeeds on every origin. A failure
  counts only when every origin reports one (the transfer is deferred); mixed
  answers are a temporary stop. Gas limit = `ceil(max simulated gas ×
  gasAdjustmentPercent / 100) + gasHeadroom`, at most `maxGas` (the processing
  record of the v2 upgrade alone adds about 22k gas; a fixed tight limit is
  never used); fee = gas limit × price, at most `maxFee`; the balance covers it.

### Signed transaction

One `TxRaw` with exactly one `MsgSubmitAttestation` whose fields are the
approval request's fields verbatim (route ID, direction, source chain ID,
source reference, nonce, destination, amount, deadline, the stored 65-byte
approvals), no memo, timeout, extension option or unordered flag; one signer
info with the `/cosmos.evm.crypto.v1.ethsecp256k1.PubKey` compressed key,
`SIGN_MODE_DIRECT` and the account sequence; one `axtc` fee coin without payer
or granter. The signature is the low-S `R || S || V` (V in {0, 1}) signature of
Keccak-256 of the `SignDoc` (body, auth info, chain ID `xitcoin-testnet-v2-1`,
account number), as the chain's eth_secp256k1 keyring produces. The
transaction hash is SHA-256 of the `TxRaw` bytes (the CometBFT hash and the
`tx_hash` of the attestation record). The encoder is checked byte for byte
against `test/fixtures/xitcoin-chain-vectors.json`, which CI regenerates with
the chain's own Go code at the pinned commit.

The sequence is owned like a Cronos nonce: after the first transfer the
chain's sequence must equal the ledger's next nonce (`account_sequence_not_owned`
halts otherwise), and the ledger reserves each sequence for one transfer
forever. The bytes, hash and sequence are committed to the ledger, then
RelayStore records `submitted`, then the broadcast marker is committed and the
identical bytes are sent with `broadcast_tx_sync` to every origin. Send results
are never decision inputs.

Before the first send, the stored bytes are decoded and re-checked (message
equal to the request, our key, the row's sequence, gas and fee caps, valid
signature for the account number). Once the local clock says the deadline
margin is lost, they are sent unless a strict majority reports the route
paused or a base fee their fee does not cover. Otherwise strict-majority reads
decide: the sequence (unanimous: consumed halts `nonce_consumed_before_send`,
regressed halts; otherwise it waits), the route state, whether the fee covers
the base fee and minimum gas price (otherwise it waits, `fee_below_required`),
the attestation (processed elsewhere: send once anyway so the reserved
sequence is consumed), the latest block time and a simulation of the exact
signed transaction.

### Confirmation

Our transaction is recognised by its signed content, not only by its hash:
pos-chain's eth_secp256k1 verifier (`crypto/ethsecp256k1`,
`verifySignatureECDSA`) drops a 65th signature byte without checking it and
also accepts a 64-byte `R || S`, and the SDK's `TxRaw` decoder accepts a
repeated `body_bytes` field (the last wins) and overlong field tags. Anyone who
has seen our bytes can therefore re-wrap the same body, auth info and `R || S`
into another `TxRaw` with another hash, which spends our sequence and fee
exactly as ours would. Such a re-encoding is our signed transaction; when it
lands first it is recognised in the block that consumed our sequence.

A transfer completes only when: the transaction that consumed our sequence
carries our signed content, a strict majority of origins returns its
`tx_search` result identically (both of two origins, two of three) with result
code `0` and our `acc_seq` event, the block at that height is identical on
every origin and lists it, it has `confirmations` blocks on top, and the
attestation query reports `PROCESSED` on every origin with a record naming
that transaction and height and every field of our approval (route ID,
direction, source chain and reference, nonce, recipient, amount, deadline,
destination chain ID, payload hash, signing digest, signer set version and the
approvers in submission order). Our own bytes then end `finalized`; a
re-encoding ends `released_elsewhere` with its own hash, so RelayStore's
`release_ref` names the transaction that actually executed (`destination_ref`
keeps naming ours). Only then does RelayStore record `completed`. A successful
transaction whose record differs halts (`record_mismatch_after_success`).

### Releases by other transactions

`MsgSubmitAttestation` is accepted from any account holding valid approvals,
so another account may process a deposit first, for example by copying our
pending message. The recipient then received exactly the approved amount.
When every origin reports `PROCESSED` with an identical record whose approved
fields (route ID, direction, source chain and reference, nonce, recipient,
amount, destination chain ID) match, the record's transaction is committed
with code `0` at the record height in a block every origin agrees on, and that
block has `confirmations` blocks on top, the ledger records
`released_elsewhere` with that transaction and block, RelayStore records
`completed` (`release_ref` names that transaction; `destination_ref` only ever
names ours, or none) and the queue moves on.

- Before any claim: no transaction is sent.
- After our bytes were committed but before their first send, or while they are
  unknown with our sequence unused: the identical bytes are sent once anyway.
  They fail with "already processed", consuming the reserved sequence, and are
  then recorded as released elsewhere.
- A record for this deposit whose approved fields differ (only a compromised
  signer quorum, or a lying origin, produces one) halts
  (`processed_with_mismatching_record`) even when a single origin returns it: a
  halt is preferred to an alert. With three or more origins this remains true;
  run origins you trust not to lie.
- `PROCESSED_WITHOUT_RECORD` on every origin (processed before records were
  kept; impossible on a route that never processed a deposit before the v2
  upgrade) is a persistent non-blocking `release_unverified` alert.

### Recovery decisions

All from canonical observations, never from send errors. The account sequence
on every origin decides the branch first.

| Observation | Action |
| --- | --- |
| sequences differ between origins | wait (propagation) |
| account sequence below our row's | halt `account_sequence_regressed` |
| sequence unused, our signed content (our bytes or a re-encoding) in any origin's mempool, or a listing not complete | wait |
| sequence unused, nothing in flight, route usable, our fee covers the base fee and minimum gas price a strict majority reports, attempts left | resend the identical bytes (also after the deadline or a release elsewhere, to consume the sequence) |
| sequence unused, nothing in flight, fee below what would be admitted now | wait (`fee_below_required`) |
| sequence unused, nothing in flight, attempts exhausted | wait (`broadcast_attempts_exhausted`); never a halt |
| sequence consumed in a block that holds no transaction with our signed content | halt `nonce_consumed_without_inclusion` |
| sequence consumed by our signed content, its result not served by a strict majority, block recent | wait (indexing lag) |
| the same, block deeper than 100 blocks | settled from consensus state: a record naming it and our approval completes it, a record naming another transaction is a release elsewhere, otherwise `release_unverified` (`inclusion_history_unserved`); never a halt |
| origins return different blocks or a result for a block that does not list it | temporary stop (`rpc_disagreement`) |
| included, fewer than `confirmations` blocks on top | wait |
| code `0` and a record naming it with our approval | `finalized` (our bytes) or `released_elsewhere` (a re-encoding); RelayStore `completed` |
| code `0` and any other record | halt `record_mismatch_after_success` |
| failed with our `acc_seq`, processed by another transaction | `released_elsewhere` |
| failed with our `acc_seq`, record naming it | halt `record_names_failed_transaction` |
| failed with our `acc_seq`, block time after the deadline | `expired` (non-blocking) |
| failed with our `acc_seq`, a lasting condition at both heights (below) | `reverted` with the cause (non-blocking) |
| failed with our `acc_seq`, history before it no longer served | `release_unverified` (`failure_history_unserved`) |
| any other failure, including out of gas | `failed`; stop; never retried |
| consumed before the last `historyBlocks` blocks, no record naming our own transaction | halt `nonce_consumed_without_inclusion` |

Liveness of an unused sequence. A transaction evicted from mempools, rejected
at admission or rejected by the ante handler at execution (for example a fee
below a base fee that rose up to 12.5% per full block, which an outsider can
cause by filling blocks) leaves our sequence unused, and the signed bytes stay
valid for anyone to submit. That is never a persisted halt: the identical
bytes are resent only when nothing carrying our signed content is in any
mempool and their fee would be admitted now, so attempts are spent on sends
that can be admitted; once the attempts are spent the row waits. CometBFT
removes rejected and evicted transactions from its mempool cache by default
(`keep-invalid-txs-in-cache = false`, required on every origin), so identical
bytes can be readmitted. `feeMultiplierPercent` must be at least 150 so that
the fee keeps headroom over base-fee rises between signing and execution.
Re-signing the same message at the same sequence with a higher fee is not
done: two different signed transactions for one sequence would break the
ledger's one-transaction rule, and the base fee falls again once blocks are
no longer full.

Failure classification. A failed message still ran the ante handler, which
consumed our sequence and reported it as the `tx` event `acc_seq`
(`account/sequence`); a transaction rejected by the ante handler at execution
carries no such event and leaves the sequence unused. For a failed message,
state is read with height-pinned queries at the end of the block before ours
and at the end of ours on every origin; a condition counts only when it holds
at both: route paused or disabled (`route_paused`), signer set rotated
(`signer_set_rotated`), amount above the transfer limit
(`transfer_limit_exceeded`), daily limit exhausted for that UTC day
(`daily_limit_exhausted`), outstanding cap reached
(`outstanding_limit_reached`). A change made by another transaction in the same
block is never taken as the cause; such a failure stays `failed` for review.
Out of gas (gas used at the limit) is always `failed`. Recent history an
origin does not serve is a temporary stop; history older than `historyBlocks`
that an origin explicitly refuses ends in the `release_unverified` alert.

Every persisted halt is based on state and blocks every origin returns
identically and on transaction results a strict majority of origins returns
identically (both of two, two of three), except a mismatching processing record
from a single origin (above). A transaction result that only a minority of
origins returns (for example one origin answering for old history the others
no longer index) is never used: with no strict majority it fails closed to a
wait, a completion only on consensus state, or the non-blocking
`release_unverified` alert, never a halt. As on the Cronos side, three or more
origins are needed for one faulty origin to be outvoted rather than only
ignored.

### Tests

`test/xitcoin-submitter-chain.test.js` runs the complete flow against a real
single-validator `xitcoind` built from the pinned pos-chain commit (with the v2
upgrade code: typed queries and records from genesis), started on loopback
ports with chain ID `xitcoin-testnet-v2-1`, peer exchange off and no seeds,
and a bridge route initialised in genesis with the stored route ID and
synthetic signer keys. Deposits are made on a local anvil chain to the
vendored reviewed vault, and approvals come from the coordinator's
`approveFinalizedTransfer` round with three isolated signer services that each
verify the deposit on the Cronos origins. Two fault-injecting proxies give two
independent origins. Scenarios: the chain accepts its own golden transaction
(generated by the chain's Go code) and the relayer reproduces it byte for byte;
approve, submit, `PROCESSED` and completion only after the record and
confirmations, with the simulated gas plus headroom; concurrent workers, a
later worker and an independent ledger (no second mint, `released_elsewhere`);
SIGKILL in a child process at every boundary (claimed, signed, RelayStore
submitted, broadcast marker, sent, ledger finalized, RelayStore completed)
with exactly one transaction afterwards; the chain rejecting the label route
(`ErrAttestationRouteMismatch`) and minting with the stored route ID; wrong
chain, mainnet, route and signer set (stop before any claim); RPC
disagreement on the route, on the replay state and a stalled simulation
(temporary, nothing claimed, then completion); a guardian pause until a
quorum-signed resume; an approval too close to its deadline; signed bytes first
sent after the deadline (`expired`, the next transfer proceeds); a third-party
submission before any claim (no submitter transaction) and after we signed
(our bytes consume the sequence once, then `released_elsewhere`); and a
re-encoding of our signed bytes with another signature byte, which the chain
accepts, landing first (recognised by signed content: `released_elsewhere`
with its hash, never a halt).
`test/xitcoin-adapter.test.js` covers the remaining decisions against a
deterministic model of the origins: ante-handler failures, consumed and
regressed sequences, failure classification at both heights, history no longer
served, mismatching records from one origin, strict-majority sends with three
origins, stored-byte tampering, re-encodings with any 65th byte or 64-byte
signatures (also next to our own ante-rejected bytes in one block), resends
gated on the fee and on nothing in flight with exhausted attempts waiting, and
old transaction results from a minority of origins that can never force a
halt while a strict majority of three can. `test/xitcoin-transaction.test.js` and
`test/xitcoin-rpc.test.js` cover the encoding (chain vectors, strict decoding)
and every normalizer. CI builds `xitcoind` at the pinned commit (cached by
commit, Go version and runner) and runs these tests on every change; locally
they are skipped only when `XITCOIND_BIN` or Foundry is missing.

These tests do not contact Xitcoin or Cronos testnet, use real keys or prove
behaviour under power loss. The testnet's fee parameters, its REST and RPC
providers and the v2 upgrade itself must still be confirmed in the controlled
canary.

### Deployment requirements (not performed by this repository)

- Deploy `xitcoin-security-hardening-v2` on `xitcoin-testnet-v2-1` first and
  confirm on independent nodes that the typed queries answer, that the route
  ID is `0x21121c16…5cd9` and that `signer_set_version` is `1`. Confirm that
  the testnet binary's bridge and SDK encodings match `chainSchemaCommit`
  (`scripts/check-chain-fixtures.sh` against the deployed source).
- Provision a dedicated submitter account funded with test XTC only and used by
  no other program, Cosmos or EVM: an EVM transaction from the same key uses
  the same sequence and halts the submitter. Its encrypted keystore, the
  encrypted `keystore-password` credential, a private `StateDirectory` (mode
  `0700`) for the ledger, and loopback tunnels to three or more independent
  operators' CometBFT RPC and REST APIs and Cronos RPC providers.
- Share the RelayStore with the coordinator through the same reviewed
  arrangement as the Cronos submitter; this submitter performs only the
  `approved -> submitted -> completed` transitions of inbound (Cronos source)
  transfers.
- Set `maxGasPrice`, `feeMultiplierPercent` and `maxFee` from the testnet's
  actual fee market parameters.
- Back up the ledger like a key; never delete, copy between hosts or restore an
  old copy.

## Remaining before the bridge can run end to end

- Coordinator re-issue of expired approvals for transfers already `approved`
  but not submitted (both submitters defer them and wait).
- Reconciler chain readers (vault locked balance and chain outstanding amount).
- An offline review procedure for halted or failed ledger rows, and a reviewed
  completion tool for `release_unverified`, `expired` and `reverted` rows.
- Light-client verification of the attestation record (`abci_query` with
  `prove=true` against a verified header). The submitter trusts the agreement
  of independent origins instead.
- Deployment: the v2 upgrade on testnet, manifests, identities and tunnels, a
  preflight extension for both submitter manifests, the controlled canary in
  both directions and an independent security review. Mainnet is rejected in
  this release.
